# ISOMORPH — Winning Criteria

## What Judges Are Evaluating

IBM Bob 2.0 Hackathon judges evaluate:
1. Technical depth and originality
2. Quality of IBM Bob integration
3. Real-world problem validity
4. Demo quality and comprehensibility
5. Code quality and production readiness
6. Business value clarity

This document defines what "winning" looks like for ISOMORPH against each criterion.

---

## Criterion 1: Technical Depth and Originality

### What Winning Looks Like

The deterministic structural analysis pipeline is the technical moat.
No other hackathon submission will have built a custom CST-level structural differ.
Most submissions will use raw LLM over raw text.
ISOMORPH's differentiator: **the LLM never sees what the parser can determine.**

### What We Must Demonstrate

- Tree-sitter CST parsing with visible intermediate representation
- Custom structural matching algorithm (not just `git diff --word-diff`)
- Explicit node-level risk classification with named signals
- Reproducible ChangeProof with content hash
- Separation between deterministic layer and AI layer

### Failure Mode to Avoid

If the structural diff engine is shallow (e.g., just line-based diffing with AST labels), the technical depth claim collapses. The engine must produce real CST node diffs, not text diffs with AST aesthetics.

### Evidence of Success

- Structural diff correctly classifies 25+ cosmetic changes as COSMETIC and 1 logic change as HIGH in the demo corpus
- Unit tests for the differ pass and cover the core classification cases
- The intermediate representation (StructuralDiff JSON) is visible and interpretable

## Criterion 2: IBM Bob Integration Quality

### What Winning Looks Like

Bob is integrated at exactly the right level of abstraction. Bob reasons about structural signals — it does not read raw code. This is architecturally sophisticated and demonstrably different from "wrap GPT around a file."

### What We Must Demonstrate

- Bob receives structured input (RiskEntry + minimal node text), not raw file dumps
- Bob's output (AIAnnotation) is structured JSON, not free-form chat
- Bob is used for three distinct, well-motivated purposes: explanation, test generation, impact assessment
- Bob's uncertainty is preserved and surfaced
- Prompt templates are versioned and visible (not hidden black boxes)

### Failure Mode to Avoid

If the Bob integration is a simple "here is the code, tell me what changed" prompt, it looks like every other submission. The architectural choice to give Bob only structurally isolated context must be visible and explainable.

### Evidence of Success

- Demo shows Bob receiving a small, structured input and producing a specific, accurate explanation
- Test stubs generated by Bob are syntactically valid and target the exact changed behavior
- ChangeProof records the Bob model version used (provenance)

## Criterion 3: Real-World Problem Validity

### What Winning Looks Like

The problem statement resonates immediately. Every developer who has reviewed an AI-generated PR has experienced the wall-of-red-green comprehension problem. The demo scenario is realistic, not contrived.

### What We Must Demonstrate

- The demo bug (guard clause removed) is a real class of incident
- The 847-line diff is representative of real AI agent output
- The business consequence (negative prices) is immediately comprehensible
- We do not fabricate statistics or customer claims

### Failure Mode to Avoid

Inventing statistics ("ISOMORPH reduces review time by 73%"), fabricating case studies, or using unrealistic demo scenarios (trivial 3-line changes) destroys credibility.

### Evidence of Success

- Demo scenario is described accurately (demo corpus is the evidence)
- Business value section explains the AI adoption risk problem without invented numbers
- The one-line summary is immediately comprehensible to a non-technical judge

## Criterion 4: Demo Quality

### What Winning Looks Like

The demo is the product. The 90-second path is rehearsed to the point of predictability. Every visual element serves the narrative. No dead time, no fumbling, no fallback mode visible.

### What We Must Demonstrate

- 0–15s: Problem is obvious (wall of diff)
- 15–30s: Structural analysis runs and produces clean signal
- 30–50s: Risk region highlighted, Bob explanation visible
- 50–70s: Test runs, fails, output visible
- 70–90s: ChangeProof shown, hash called out

### Failure Mode to Avoid

Loading spinners longer than 1 second, Bob API error visible, cluttered UI showing non-demo features, explaining the UI instead of showing the product.

### Evidence of Success

- Demo is recorded end-to-end at 1080p before submission
- All Suite 6 tests pass (demo corpus locked)
- Fallback (cached Bob) tested and verified

## Criterion 5: Code Quality and Production Readiness

### What Winning Looks Like

The repository looks like a real open-source project. Clean structure, working tests, working Docker setup, meaningful README with setup instructions.

### What We Must Demonstrate

- `docker-compose up` brings up working backend + frontend
- `pytest` runs and passes all automated test suites
- TypeScript compiles with strict mode, no type errors
- README explains the project in 5 paragraphs and has a working quickstart
- No TODO comments in production paths
- No `print()` debug statements in production paths

### Failure Mode to Avoid

Broken build, missing dependencies, tests that are commented out, environment variables that aren't documented, a repo that requires setup steps not in the README.

### Evidence of Success

- CI (GitHub Actions) passes on the main branch
- A fresh `git clone` + `docker-compose up` produces the working demo

## Criterion 6: Business Value Clarity

### What Winning Looks Like

Any judge — technical or business — can state the product value in one sentence after the demo. The value is about AI adoption risk, review efficiency, and audit trails.

### What We Must Demonstrate

- The problem is framed in terms of business consequence (incidents, audit, AI adoption)
- The output (ChangeProof) is framed as a business artifact, not a developer tool
- The value proposition is visible in the UI (not just in a pitch deck)

### Failure Mode to Avoid

Framing the product as a developer productivity tool only. The ChangeProof as audit artifact has compliance and enterprise value that must be visible.

### Evidence of Success

- "Change Proof" language appears in the UI header/panel — not hidden in JSON
- The demo scenario connects structural analysis to a business consequence (negative prices)

## The Differentiation Test

Before submission, apply this test to every component:

> "Could this component be replaced by: (a) an existing tool, or (b) a simple LLM prompt over raw code?"

If the answer is yes, that component is not a differentiator.

| Component | Differentiation Test | Verdict |
|---|---|---|
| Tree-sitter CST parsing | No existing diff tool uses this for review | ✅ Differentiator |
| Structural diff algorithm | No existing review tool diffs at CST node level | ✅ Differentiator |
| Risk signal classification | No existing tool has this taxonomy | ✅ Differentiator |
| Bob receiving structured IR | Architecturally different from raw code prompt | ✅ Differentiator |
| ChangeProof with content hash | No existing tool produces this artifact | ✅ Differentiator |
| Test stub execution as evidence | Behavioral evidence, not inference | ✅ Differentiator |
| General AI explanation of code | Can be done with any LLM on raw code | ❌ Not unique alone |
| PR comment generation | GitHub Copilot, CodeRabbit do this | ❌ Not unique, excluded |

## Kill List: What Would Make This Look Ordinary

These features, if present, would signal "another AI code reviewer":

1. ❌ Chat interface for asking questions about the code
2. ❌ "Issues found" list with severity scores but no structural basis
3. ❌ Generic vulnerability scanning (OWASP categories, etc.)
4. ❌ PR automation (auto-comment, auto-approve)
5. ❌ Similarity to existing tools: CodeClimate, SonarQube, CodeRabbit, Reviewpad
6. ❌ Any claim of semantic equivalence or "proving code is correct"
7. ❌ Dashboard with arbitrary metrics (lines analyzed, repos scanned)
8. ❌ "AI-powered" as a selling point rather than a specific capability claim
9. ❌ Raw file ingestion into Bob without structural pre-processing
10. ❌ Explaining what code does (general) rather than explaining what changed (specific)

## Minimum Complete Product Surface

The minimum surface that creates a convincing end-to-end proof:

1. **Structural diff engine** — Python, working, unit-tested
2. **Risk classifier** — rule-based, deterministic, unit-tested
3. **Bob orchestrator** — three prompt types, structured I/O, cached fallback
4. **ChangeProof assembler** — schema-valid, reproducible, content-hashed
5. **FastAPI endpoint** — POST /api/analyze, schema-validated
6. **Demo corpus** — before/after Python files, locked by Suite 6 tests
7. **Evidence runner** — test stub execution, subprocess isolated
8. **Structural diff UI** — not a text diff viewer, shows CST regions
9. **Risk panel** — HIGH/MEDIUM/LOW/COSMETIC breakdown
10. **ChangeProof panel** — hash visible, JSON downloadable

Everything else is stretch. Nothing else gets built until these 10 are complete and tested.
